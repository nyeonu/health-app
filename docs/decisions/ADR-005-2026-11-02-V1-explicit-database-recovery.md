# ADR-005: 확인된 이력 삭제로 손상된 SQLite 파일을 복구

## 상태
Proposed

## 날짜
2026-11-02

## 티켓
V1

## 배경
PR #8 검토에서 payload가 아닌 SQLite 스키마/파일 자체가 손상되면 기존 reset이 동일한 열기 검증에서 계속 실패함을 확인했다. 소유자는 코멘트 처리, 별도 세션 검증, 이슈 해소 후 개발 PR 병합을 요청했다. 읽기 실패만으로 초기화하지 않으며, 확인된 삭제 이후에는 과거 이력의 백업도 남기지 않는 기존 계약을 유지한다.

## 결정
정상 SQLite의 빈 상태 저장은 기존 DELETE/FULL 트랜잭션을 유지한다. 사용자 확인을 받은 reset에 한해 정상 열기에 실패한 파일을 같은 디렉터리의 동기화된 복구 스냅샷으로 보호하고, 검증한 새 빈 SQLite 파일을 원자적으로 설치한 뒤 모든 이전 이력 스냅샷/임시 파일과 복구 표시를 제거한 후에만 완료를 반환한다.

같은 DB 경로의 모든 저장소 인스턴스는 연결의 열기부터 닫기까지 공통 잠금으로 직렬화한다. 복구 디렉터리의 존재는 중단된 삭제 표시이며 load/일반 replace는 명시적 오류를 반환하고 자동 복구를 실행하지 않는다. 재시도도 새 사용자 확인 경로로만 실행한다. 파일뿐 아니라 저널/WAL/SHM sidecar도 보호·정리하고, rename 및 부모 디렉터리 동기화를 확인한다.

## 검토한 대안
### 같은 SQLite 트랜잭션만 재시도
- 장점: 기존 원자성 경계를 그대로 사용한다.
- 단점: 열기 자체가 불가능한 DB에서는 삭제가 영구 실패한다.
- 기각 이유: 명시적 삭제로 지원 불가/손상 이력을 복구한다는 계약을 충족하지 못한다.

### 읽기 시 무조건 삭제 또는 AtomicFile로 main 파일만 교체
- 장점: 구현이 짧다.
- 단점: 사용자 확인 없이 기록을 잃거나 SQLite sidecar와 불일치할 수 있다.
- 기각 이유: 기존 확인·실패 보존·SQLite 일관성 계약을 위반한다.

### 손상 DB는 복구 대상에서 제외
- 장점: 새 파일 복구 프로토콜이 필요 없다.
- 단점: 명세·UI·운영 복구 정책을 축소해야 한다.
- 기각 이유: 코멘트 수정 요청은 기존 복구 계약을 구현하는 방향으로 처리한다.

## 결과와 비용
정상 경로에는 새 저장 의존성이나 형식 변경이 없다. 예외 경로에는 중단 표시·동기화·스냅샷 정리의 책임이 추가된다. 설치 전 실패는 이전 파일을 보존하거나 명시적 오류로 남기며, 설치 후 불확실성은 과거 이력을 다시 복원하지 않는다. 완료 응답은 새 빈 DB 재열기 검증과 이전 이력 파일 정리가 모두 성공한 뒤에만 허용한다. 여러 Android 프로세스에서 동시에 저장소를 사용하도록 바뀌면 JVM 공통 잠금만으로는 부족하므로 별도 검토가 필요하다. 법의학적 보안 삭제나 전원 상실에 대한 하드웨어 보장은 하지 않는다.

일반 조회는 미지원 파일의 저널 모드를 바꾸지 않도록 읽기 전용으로 검사한다. 실제 hot rollback journal을 읽기 전용으로 복구할 수 없으면 명시적 저장소 오류로 남겨 사용자 확인 reset으로 복구한다. 이 상태를 빈 이력이나 자동 복구 성공으로 표시하지 않는다.

ADR-004의 정상 트랜잭션 결정은 유지하며, 이 ADR은 열 수 없는 DB의 명시적 복구를 보완한다. 실제 Galaxy/TalkBack 수용 및 출시 승인은 별도이며 미수행 항목을 완료로 바꾸지 않는다.
