# ADR-004: 수동 동기화 이력을 기본 SQLite 트랜잭션으로 보관

## 상태
Proposed

## 날짜
2026-11-01

## 티켓
V1

## 배경
승인된 V1 첫 단계는 마지막 시도와 마지막으로 확인된 성공을 앱 재실행 후에도 구분해서 보여준다. 기존 ViewModel은 상태와 토큰을 메모리에만 보관한다. 새 이력에는 인증 토큰, 계정·원격 파일 식별자, 건강 수치나 CSV 본문을 저장하지 않으며, 현재 계정의 원격 완료 여부를 추정하는 근거로 사용하지 않는다. 삭제와 저장 실패는 기존 성공 보존 및 실제 저장소 재개방 검증이 필요하다.

## 결정
Android 기본 SQLite의 앱 전용 백업 제외 위치에 버전이 있는 단일 이력 레코드를 보관한다. 마지막 시도·성공의 교체와 빈 상태로의 삭제는 각각 하나의 트랜잭션으로 커밋하고, 상태 판정·포맷 검증은 순수 Kotlin core에 둔다. 플랫폼 저장 어댑터와 직렬화된 세션 조정자는 Android app에 두되, 토큰·동의는 계속 메모리에만 보관한다.

## 검토한 대안
### SharedPreferences
- 장점: 작은 설정 값을 저장하기 쉽고 별도 의존성이 필요 없다.
- 단점: 이 계획에서 요구하는 명시적 트랜잭션 경계와 실패 주입·실제 재개방 검증을 표현하기 어렵다.
- 기각 이유: 단순 설정 저장보다 커밋·롤백과 삭제 복구의 판별이 핵심이다.

### 직접 파일 교체·저널 구현
- 장점: 작은 메타데이터 파일 하나로 표현할 수 있다.
- 단점: 커밋 확인, 이전 상태 보존, 중단 시 복구 프로토콜을 직접 설계·유지해야 한다.
- 기각 이유: 플랫폼 트랜잭션으로 해결 가능한 원자성 로직을 새로 만들지 않는다.

### Room 또는 새 저장 프레임워크
- 장점: 스키마와 쿼리 추상화를 제공한다.
- 단점: 단일 레코드에 새 런타임·빌드 의존성과 마이그레이션 체계를 추가한다.
- 기각 이유: 현 단계는 플랫폼 SQLite로 요구사항을 검증할 수 있다.

## 결과와 비용
추가 의존성 없이 원자적 교체·삭제를 실제 SQLite로 검증할 수 있으나, 포맷·스키마 버전 및 실패 분류 책임은 앱에 남는다. 읽기 실패를 빈 상태로 바꾸거나 파괴적인 초기화로 숨기지 않는다. 저장 커밋의 불확실성은 명시적인 오류와 재개방으로 처리하며, SQLite 보장은 Drive 쓰기의 롤백이나 하드웨어 무결성 보장이 아니다. 향후 계정별 날짜 범위, 다중 저장 대상, 백그라운드 실행이 추가되면 별도 설계 검토가 필요하다.

이 ADR은 계획 승인 직후의 결정 기록이며 구현 완료 증거가 아니다. P0 잔여 검증은 그대로 남아 있고, 스펙 적합성 검증 통과 전까지 Proposed를 유지한다.
